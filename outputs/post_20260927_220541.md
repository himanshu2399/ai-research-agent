### Topic
ReadOnlyRootFilesystem isn’t enough: Kubernetes v1.37 lets you actually block exec on writable volumes

### Research Summary
- Problem: Teams often set readOnlyRootFilesystem: true and assume the container can’t execute untrusted code. But execution is governed by mount options. If a writable volume is executable (the default), malware can write to /tmp or other scratch space and run from there.
- What’s new in v1.37: 
  - Per-volume bindMountOptions (noexec, nosuid, nodev) to disable execution and tighten mounts.
  - emptyDir can now set explicit permission modes (e.g., 01777 for shared /tmp or 0750 for private scratch) without init-container workarounds.
- Status and caveats: Both are Alpha behind feature gates (VolumeBindMountOptions, EmptyDirVolumeMode), require runtime support, and apply to Linux only.
- Practical impact: Platform teams can finally enforce “noexec on anything writable” and set sane emptyDir permissions as a baseline, reducing a common attack path with limited app changes—if rolled out carefully.

### LinkedIn Post
“Read-only” containers still run code from /tmp.

readOnlyRootFilesystem only locks the image layers. The moment you add a writable volume (emptyDir, PVC, workspace), attackers can drop a binary in /tmp and execute it like nothing happened.

Kubernetes v1.37 finally closes this gap:
- Native bindMountOptions per volume: noexec, nosuid, nodev.
- emptyDir can set real permission modes (e.g., 01777 sticky bit) without init hacks.

Both are Alpha behind feature gates (VolumeBindMountOptions, EmptyDirVolumeMode) and need runtime support. Linux only for now.

Why this matters: exec-ability is a mount property. If a writable mount is executable, malware doesn’t need your root filesystem. It just needs a place to write. Cutting exec from scratch space removes a whole attack path with minimal app impact—if you roll it out smartly.

My sane defaults for platform teams:
- noexec,nosuid (and nodev when possible) on all writable app mounts.
- emptyDir.mode:
  - 01777 for shared /tmp (sticky bit protects cross-user files).
  - 0750 for private scratch.

Expect some breakage:
- Installers or tools that unpack to /tmp and exec.
- Scripts that assume 0777 everywhere.
- Anything relying on suid on mounted paths.

Rollout plan:
- Enable the gates in a test cluster; verify your runtime advertises bind mount option support.
- Measure failures: try copying /bin/sh to /tmp and executing it. If it runs, you’re exposed.
- Add an admission policy to require noexec on writable mounts; allow time-boxed exceptions with clear owners.

Question for platform teams: would you enforce noexec + sane emptyDir modes org-wide by default, or let app teams opt in? Where would you draw the line?
