### Topic
Using AWS CodeDeploy RESTART mode to orchestrate EC2 fleet restarts safely

### Research Summary
AWS introduced a purpose-built RESTART deployment mode in CodeDeploy that reapplies the last successful revision to EC2 and on-prem fleets while handling reboots with standard deployment guardrails. Per AWS’s post “Restart EC2 and on-premises fleets faster with AWS CodeDeploy RESTART deployment mode,” RESTART maintains batch sizing, health checks, alarm monitoring, and rollback behavior, and their testing reported up to 6.1x faster restarts. This keeps restarts inside the deployment pipeline instead of relying on brittle scripts or ad-hoc playbooks. Key insight: treat reboots as deployments to gain the same safety rails and potentially reduce restart time.

### LinkedIn Post
Stop treating reboots as “just an ops chore.” They’re deployments—usually with fewer guardrails.

If you’ve been rolling EC2 restarts with ad‑hoc scripts, you often trade safety for speed: wider blast radius, weaker health checks, and no automatic rollback. AWS changed the calculus: CodeDeploy now has a purpose‑built RESTART mode that reapplies the last successful revision and handles the reboot as a first‑class deployment.

The win isn’t magic—it’s discipline. RESTART keeps the same safety rails you already trust for code changes: batch sizing, health checks, alarm monitoring, and rollback behavior. AWS reported restarts up to 6.1x faster in their testing, and—more importantly—you keep reboots inside your delivery pipeline instead of scattered cron jobs and playbooks.

Practical angle:
- Treat a reboot like any other risky change. Start with conservative batch sizes to cap blast radius.
- Wire alarms to user‑visible health, not just instance metrics. If they trip, rollback limits the damage.
- Because RESTART reapplies the last successful revision, it helps reduce “works after reboot… except we drifted” surprises.

Why this matters: speed and safety aren’t foes here. Orchestrated restarts can shorten bounce windows when you must reboot a fleet, while preserving the same operational contracts your team relies on for deployments.

Looking ahead, the more we make reboots declarative and pipeline‑driven, the less we need bespoke playbooks and midnight heroics. One mental model for SREs: if it changes the instance state, it belongs in the deployment system.

How are you coordinating EC2 restarts today—scripts, ASG tricks, or something else? If you use CodeDeploy, what would stop you from flipping to RESTART for fleet reboots?
