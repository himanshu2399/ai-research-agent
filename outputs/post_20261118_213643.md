### Topic
Migrating Kubernetes clusters from kube-proxy IPVS to nftables before removal

### Research Summary
- Kubernetes SIG Network deprecated the kube-proxy IPVS backend in v1.35 and plans to remove it in v1.40 due to feature gaps, maintenance burden, and scaling limitations.
- nftables is GA (since v1.33) and is the recommended path on Kubernetes v1.36+ with Linux kernel 5.13+. It provides full feature coverage and comparable or slightly better latency.
- iptables mode has received significant optimizations and remains a viable fallback.
- IPVS schedulers don’t provide meaningful benefits given kube-proxy’s distributed design.
- Distro plans (e.g., RHEL dropping the iptables API) further undermine IPVS longevity.
- Key takeaway: Teams still on IPVS should plan migration soon—nftables is supported without performance tradeoffs; delaying invites breakage by v1.40 and distro-level incompatibilities.

### LinkedIn Post
Still running kube-proxy in IPVS because “it’s faster”? That belief used to be handy. It’s now technical debt.

SIG Network has deprecated the IPVS backend (v1.35) and plans to remove it in v1.40. The why: feature gaps, maintenance burden, and scaling limits. Meanwhile, nftables is GA, recommended on Kubernetes v1.36+ with Linux kernel 5.13+, and delivers full feature coverage with comparable—or slightly better—latency. iptables mode has also seen real optimizations.

Here’s the kicker: those IPVS schedulers you’ve been tuning don’t meaningfully help in kube-proxy’s distributed design. You’re twisting knobs that don’t move the needle.

Why this matters:
- Waiting risks breakage when you upgrade to v1.40.
- Distro shifts (like plans to drop the iptables API) further undermine IPVS.
- You’re burning cycles on a path that’s already closing.

Practical take:
- Treat nftables as the default migration target if you’re on supported versions (Kubernetes v1.36+ and Linux kernel 5.13+).
- Keep iptables as a viable fallback; it’s been optimized too.
- Stop investing effort in IPVS scheduler tuning. Move that energy into validating nftables behavior under your real traffic patterns and failure modes.

Forward look: kube-proxy mode needs to become part of your platform baseline, not a per-node preference. The sooner you standardize on nftables, the less surprise shows up in your next upgrade window.

What’s honestly blocking your move—kernel floor, distro constraints, or fear of perf regressions? If you’ve already switched, did you see any meaningful latency change?
